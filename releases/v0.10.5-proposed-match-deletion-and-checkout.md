# v0.10.5 — Proposed Match Deletion Memory & Checkout Replacement

## DB Migration

Run in Supabase SQL editor **before deploying**:

```sql
ALTER TABLE proposed_matches ADD COLUMN deleted_at timestamptz;
```

## Problem 1: Deleted match re-added immediately

### Root cause
`deleteProposedMatch` hard-deleted the row. On the next "Add Matches" call,
`proposeNextMatches` had no memory the group was ever rejected. The scoring
function scored it the same as any other combination — often best, since it
was previously chosen for good skill balance — and re-picked it.

### Fix
**Soft-delete**: `deleteProposedMatch` now sets `deleted_at = now()` instead
of removing the row.

In `proposeNextMatches`, two separate queries are made:
- `existingProposed` — active rows only (`deleted_at IS NULL`) — these drive wave
  logic and the 4-match target count.
- `deletedProposed` — soft-deleted rows (`deleted_at IS NOT NULL`) — loaded and
  prepended to `workingHistory`.

Because `workingHistory` is passed to `scoreMatch`, the -5000 exact-duplicate
penalty fires for any group whose 4-player combination matches a deleted proposal.
The group can still be selected if it is the only viable option (score wins at
-4000 vs -Infinity), satisfying the "last resort" requirement.

`getProposedMatches` adds `.is("deleted_at", null)` so deleted matches never
appear in the UI.

## Problem 2: Checkout leaves proposed matches with absent player

### Fix
New exported function `replacePlayerInProposedMatches(sessionId, departedPlayerId)`:

1. Queries all active proposed matches containing the departed player.
2. For each affected match, builds a set of players locked in OTHER proposed
   matches (to avoid double-booking).
3. From the remaining checked-in players, finds the candidate that minimises
   `|new_team_skill - opposing_team_skill|`.
4. If a candidate exists: updates the departed player's slot with the replacement
   and recalculates `avg_skill_diff`.
5. If no candidate exists: soft-deletes the match (same mechanism as manual
   deletion, so the group is penalised on next generation).

The working snapshot (`activeSnapshot`) is updated after each match so
subsequent iterations see the correct locked state.

Called from `POST /api/sessions/[id]/checkout` after the session_players row
is updated.
