# v0.39.0 — Season Newsletter

Date: 2026-05-15

## Overview

Adds an admin-only **season newsletter** feature. The newsletter is auto-generated from real season match data and persisted in the database so it can be regenerated, versioned, and surfaced anywhere in the app.

## DB migration

New table `public.season_newsletters` (one row per season, keyed by `season_id`).

| Column | Type | Notes |
|---|---|---|
| `season_id` | uuid | PK, FK → `seasons.id`, `on delete cascade` |
| `title` | text | Display title (e.g. "Spring 2026 — Season Recap") |
| `content_md` | text | Generated markdown body |
| `intro_context` | text | Optional admin-provided anecdotes folded into the intro |
| `stats_json` | jsonb | Snapshot of the stats the newsletter was generated from |
| `version` | int | Monotonically increasing — incremented by trigger on every update |
| `generated_by` | uuid | FK → `players.id`, `on delete set null` |
| `created_at`, `updated_at` | timestamptz | `updated_at` auto-bumped by trigger |

Migration name: `season_newsletters`.

## Admin behavior

- The newsletter route is wrapped in `getAuthPlayer().isAdmin` — non-admins are redirected to `/`
- On first visit for a season with no row in `season_newsletters`, the page calls `getSeasonStats(...)` + `generateNewsletter(...)` and `upsertNewsletter(...)` so the DB always has the current version saved
- The "Regenerate with this context" button calls `POST /api/admin/seasons/[id]/newsletter` with the textarea contents. The same endpoint with empty body regenerates a stats-only version

## Stats scope

`getSeasonStats(seasonId)` only counts non-test, regular, completed sessions on or before the season's `stats_lock_date` (falls back to `end_date`). Tally-mode and full match-detail sessions are both consumed; per-player W/L takes the max of the two sources to avoid double-counting whiteboard nights.
