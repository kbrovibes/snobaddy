# v0.15.5 — Match Queue Backfill Fixes

## Summary

Three bugs in the match proposal pipeline caused the queue to fail to backfill
reliably and to repeat the same pairings after deletion. All three are fixed.

## Root Causes

### Bug 1: Fire-and-forget backfill in matches route

`src/app/api/matches/route.ts` called `backfillMatchQueue().catch(() => {})`.
The HTTP response was returned before the async backfill completed. The client's
`router.refresh()` then fetched stale data (no new proposal yet).

**Fix:** `await backfillMatchQueue(session_id)` before returning.

### Bug 2: Delete route never triggered backfill

`src/app/api/proposed-matches/[id]/route.ts` soft-deleted the proposal but never
called `backfillMatchQueue`. The queue stayed one short permanently until the next
unrelated trigger (e.g., a score being recorded).

**Fix:** Added `const sessionId = await deleteProposedMatch(id); if (sessionId)
await backfillMatchQueue(sessionId);`

### Bug 3: Fixed anchor in `findBestMatch()`

The algorithm always picked the same player as the "anchor" (first in Supabase's
return order). Since all combinations are anchored to one player, the scored
candidate set was identical every invocation — so the same match always won after
a deletion (the second-best was always the same second-best).

**Fix:** Added `shuffled()` helper that Fisher-Yates shuffles within each group
(rested players shuffled independently from just-played players) before the anchor
is selected. Rested-player priority is preserved; the specific anchor varies.

Also added `±10 pt` random jitter per player to the wait-time component in
`scoreMatch()` to break scoring ties between near-identical lineups.

## Files Changed

| File | Change |
|------|--------|
| `src/app/api/matches/route.ts` | `await` backfill instead of fire-and-forget |
| `src/app/api/proposed-matches/[id]/route.ts` | Add `backfillMatchQueue` call after delete |
| `src/lib/db/proposed.ts` | Add `shuffled()` helper; shuffle in `findBestMatch()`; add jitter in `scoreMatch()` |
| `journal/04-MATCH-GENERATION-ALGO.md` | Full rewrite: detailed algorithm doc with ASCII visuals, worked examples, bug post-mortem, and 9 improvement ideas |

## Sequencing note

When recording from a proposed match card, the client calls POST /api/matches
then DELETE /api/proposed-matches. The backfill in the POST is now awaited but
will be a no-op (queue still at cap while the proposed match exists). The backfill
in the DELETE generates the replacement. This is correct and intentional.
